# Fork version and branch strategy

本策略适用于 `asterayx/vllm`，于 2026-11-22 确认。
官方仓库为 `vllm-project/vllm`，Git remote 名为 `upstream`；
自己的仓库 remote 名为 `origin`。

## 分支职责

| 分支或标签 | 职责 | 更新方式 |
| --- | --- | --- |
| 官方 `v0.34.0` tag | 不变的官方发布基线 | 不移动、不覆盖官方 tag |
| `upstream-v0.34.0` | 官方 tag 的纯净分支别名 | 保持在官方提交，不接收定制修改 |
| `rtxpro5000-v0.34.0` | 当前版本的定制开发分支 | 提交修改，通过 PR 进入对应 release 分支 |
| `release/v0.34.0-rtxpro5000` | 基于 v0.34.0 的定制版本验证与维护分支 | 验证并接收定制 PR，以及必要的定向修复 |
| `main` | 官方后续更新与我们定制修改的长期集成分支 | 通过 PR 集成已验证的 release 修改及官方更新 |

`release/*` 创建时从相应官方 tag 起步；接受定制 PR 后，它就是我们的版本分支。
纯净官方基线始终由官方 tag 和 `upstream-*` 别名表示。

## 合并路径

```text
官方 v0.34.0 tag
  ├── upstream-v0.34.0                    保持纯净
  ├── rtxpro5000-v0.34.0                  开发定制修改
  └── release/v0.34.0-rtxpro5000           接收定制 PR

rtxpro5000-v0.34.0
  └── PR #28 → release/v0.34.0-rtxpro5000
                 └── 合适时另开 PR → main

官方 upstream/main
  └── 同步工作分支：合并、解决冲突、验证 → PR → main
```

1. 以官方发布 tag 为基线建立开发分支与 release 分支。
2. 将我们的修改合入开发分支，处理兼容性问题，执行相关回归、模型验证与性能测试。
3. 通过 PR 将开发分支合入 release 分支，保存测试报告与原始数据。
4. 在准备纳入长期主线时，从当前 `main` 建集成工作分支，再合并 release 分支。
   解决与较新官方实现的冲突并重新验证，通过另一个 PR 合入 `main`。

开发 PR 合入 release 不会自动将代码合入 `main`，也不等于部署服务。
每次实际合并和部署按对应任务明确执行，不启用自动合并。

## 官方更新与版本维护

- `main` 的目标是同时保留官方更新与我们的定制能力，不再作为纯净官方镜像。
  含有定制修改后，不通过强制重置或强制同步覆盖成 `upstream/main`。
- 获取官方更新后，在独立集成工作分支合并 `upstream/main`，解决冲突并验证，
  再通过 PR 进入自己的 `main`。
- `release/v0.34.0-rtxpro5000` 固定在 v0.34.0 的版本体系中维护。
  需要修复时定向 backport；不直接把较新 `main` 整体合回旧 release。
- 升级到另一官方版本时，从新 tag 建立对应的开发与 release 分支，重复上述流程。
- 不改写官方发布 tag。若需要标记定制发行，使用可区分的名称，
  例如 `v0.34.0-rtxpro5000.1`，并记录所对应的源码提交和验证报告。

## 验证与版本追溯

- 报告记录官方基线、实际源码 commit、依赖版本、GPU 配置、测试命令和原始数据。
  `vllm --version` 是安装元数据，不能代替实际源码 commit。
- 版本号中的 `dev` 和 Git hash 表示定制开发构建，不代表官方发布了同名正式版本。
  源码更新后刷新安装元数据，并核对源码路径及依赖。
- 若只调整合并历史且 Git tree 完全一致，可引用原测试，并明确没有重新执行。
  仅文档变化时，记录文档差异及实现未变化，不再声称整个 tree 完全一致。
- 向更新的 `main` 集成会改变代码组合，需要重新执行受影响的回归、模型正确性验证，
  并对性能敏感路径进行相同口径的性能测试。旧 release 的结果不能直接当成新主线结果。
- 同一版本的官方预编译扩展能否复用，要核对相关源码及 ABI 兼容性；
  本地修改 C/CUDA 或相关扩展实现时，按构建流程重新编译并验证。
